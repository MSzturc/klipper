    Profile-Guided Build¶

    What this is¶

    The host-side C helper (klippy/chelper/c_helper.so) — which handles step compression, kinematic step generation (itersolve), and the trapezoidal motion queue — is compiled with profile-guided optimization (PGO). Branch and loop counters from real klippy runs are recorded and fed back into the next compile, letting GCC inline aggressively, lay out hot basic blocks for the instruction cache, and demote cold paths.

    The optimization is fully automatic. There are no printer.cfg keys, no opt-in flags, no manual commands. The chelper rebuilds itself across two klipper service starts.

    Typical magnitude on host hot paths:

    Component Speedup vs. non-PGO
    itersolve (step time generation) ~10–25 %
    stepcompress ~10 %
    toolhead lookahead ~5–10 %

    Real magnitude depends on the SoC, kinematic mode, and workload. PGO supplements (does not replace) the existing -O3 -flto -march=native compile flags and the hot-path function attributes already present in the chelper sources.

    How the build cycle works¶

    PGO is a two-stage build that bootstraps itself. Across two klipper service starts you go from "no profile" to "optimized binary" with no manual step in between.

    Stage 1 — instrumented build. On a fresh install, no profile data exists. The first klipper start compiles c_helper.so with -fprofile-generate, producing an instrumented binary that records counters at runtime. This binary runs roughly 2–5 % slower than a regular build — measurable on a low-end SoC, invisible on faster boards. Counters are buffered in process memory; nothing is written to disk while klippy is running.

    Counter write-out. When the klipper service stops cleanly (RESTART, FIRMWARE_RESTART, sudo systemctl restart klipper), the instrumented binary's exit handler flushes the counters as *.gcda files into klippy/chelper/.pgo/. Total store size is typically a few MB.

    Stage 2 — optimized build. On the next klipper start, the build system sees the fresh counter files (their mtime is newer than the compiled .so) and recompiles c_helper.so with -fprofile-use, baking the counters into block layout, inlining decisions, and branch hints. From this point on, every klipper start runs the optimized binary, until something invalidates the profile.

    In short: after a fresh install or any chelper source update, the second service restart brings you to the fully optimized binary. Restart number 1 runs instrumented and trains; restart number 2 compiles optimized and runs from there.

    Update workflow¶

    Klipper installs are typically updated via git pull — either through Moonraker's Update Manager or by hand. PGO interacts with updates differently depending on whether the update touches the C helper sources.

    Updates that do not touch klippy/chelper/*. The vast majority of fork updates fall here: changes to klippy/extras/*.py, configuration helpers, docs, host scripts. The recorded profile is still valid for the unchanged C code. The chelper does not rebuild, the .pgo/ store is left alone, and the next klipper start continues to run the same optimized binary you had before the pull.

    Updates that touch klippy/chelper/*.c or *.h. The chelper records a SHA-256 hash of every C source and header file at training time and stores it as klippy/chelper/.pgo/source.hash. On the next klipper start after the update, the new file contents produce a different hash. The system detects the mismatch, discards the stored profile, and emits one log line:

    chelper: discarding stale PGO profile (chelper sources changed since training)

    The build then runs Stage 1 (instrumented) on that same start. The next service stop writes fresh counters that match the new code. The start after that runs Stage 2 (optimized). Two service restarts and you're back to the fully optimized binary.

    The auto-invalidate exists because the alternative — keeping a profile that partially mismatches the current code — silently degrades optimization on every changed function with no log line, no warning, no observable signal. It would slowly erode the performance benefit over many updates without anyone noticing.

    What you might notice as a user¶

    For most users, PGO is invisible. The cases where it can be perceptible:

    • First boot of a fresh THEOS image, or first start after a chelper-touching update. That single klippy session runs the instrumented binary. On a Banana Pi M2 Zero or comparable low-end SoC, per-move host work is a few percent slower. Klipper still keeps up with normal print velocities; you may see slightly higher CPU usage in htop. Subsequent restarts run the optimized binary.
    • Disk usage. ~/klipper/klippy/chelper/.pgo/ typically holds 2–5 MB of counter and hash data. It is created on demand and wiped automatically on retraining.
    • Log line after chelper-touching updates. chelper: discarding stale PGO profile (chelper sources changed since training) is normal and expected. It is not a warning. It is the system announcing the retrain cycle.

    Configuration¶

    None. PGO is always on for the chelper build.

    Manually retraining the profile¶

    You should not need to do this in normal operation. The auto-invalidate handles source updates, and a single representative session is usually enough training. There is, however, no harm in retraining manually if you want a profile captured against a more representative workload than the one your printer ran during its last instrumented session:

    rm -rf ~/klipper/klippy/chelper/.pgo
sudo systemctl restart klipper   # Stage 1: instrumented build
# (optional: run a representative print here to train against real workload)
sudo systemctl restart klipper   # Stage 2: optimized build

    The first restart runs the instrumented binary. Anything you do during that klippy session — startup, idle, a homing move, a calibration, a real print — contributes counters when klippy stops. The second restart compiles the optimized binary based on what was captured.

    Things to know¶

    • The profile is per-machine. Counters are collected against this specific SoC's branch predictor, cache hierarchy, and instruction timings. If you clone an SD card to a different printer with a different SoC, the new printer's first klipper start will detect that the prior .gcda were captured on different hardware and silently retrain (the source hash matches but the counters are typically rejected by GCC's runtime check). Two stations running identical SoCs can share .pgo/, but it's rarely worth the trouble.
    • .pgo/ is gitignored. A git pull will not overwrite, remove, or conflict on the profile directory.
    • Counter write-out requires a clean klippy exit. A power cut mid-print does not produce profile data — the SIGKILL skips the exit handler that flushes counters. This is not harmful; that particular session simply contributes nothing to the next training cycle.
    • The instrumented binary still meets real-time deadlines. The 2–5 % overhead is on host computation, not MCU communication. Klipper continues to flush move chunks ahead of the MCU exactly as it does in the optimized build, and stepcompress continues to feed clocks at the configured rate.
    • No effect on MCU firmware. PGO applies only to the host-side C helper. The MCU firmware (klipper.bin, klipper.elf) is built by make as before, with its own optimization flags, and is entirely unaffected.
    • Compilation time. A full chelper rebuild adds ~1–2 seconds on x86 and ~5–10 seconds on a Banana Pi M2 Zero, both for Stage 1 and Stage 2. This is once per cycle, not per klippy start.

    Credits¶

    Original work in this fork. Profile-guided optimization is a standard GCC feature; the contribution here is the self-bootstrapping wrapper that runs the two-stage build transparently across klipper service lifecycles, auto-detects fresh counters via mtime, and invalidates the profile on chelper source changes via a content hash check.
